## 1. 目标与范围

保留完整的南京 → 哈尔滨 → 长白山北景区 → 沈阳 → 南京十日行程，并将现有页面从旧版“太阳岛＋极地公园”内容改成原稿中的正式安排。

页面面向 2 位成人＋2 名儿童（7 岁、9 岁），优先服务两种场景：

- 出发前：确认车票、景点预约、酒店接站和天气备用方案。
- 旅行中：快速查看当天时间线、天气、交通、住宿和下一步动作。

本次不新增账号、数据库或第三方 UI 框架；沿用 React、TypeScript、CSS Modules 和现有天气 API。

## 3. 推荐界面结构

### 3.1 顶部 Hero：先回答“这趟行程是什么”

Hero 展示：

- 标题：`2026 东北亲子避暑 10 日`。
- 副标题：`8.14—8.23 · 2 大 2 小 · 南京出发`。
- 四个统计：10 天、3 个目的地、4 位同行者、1 个天气备用日。
- 一条横向路线：南京 → 哈尔滨 → 长白山 → 沈阳 → 南京。
- 首屏提示：长白山天池受天气影响；D552、长白山门票和返程车票需要按节点确认。

### 3.2 关键节点卡：把“必须记住的事”置于总览区

使用四张紧凑卡片，按时间排序：

1. 8/3 10:00：D552/D553 哈尔滨 → 长白山。
2. 8/6 16:30：G3554 长白山 → 沈阳北。
3. 8/9 09:00：G98/G99 沈阳北 → 南京南；同时检查哈工大预约。
4. 8/11 18:00：长白山北景区 8/18 门票。

卡片显示目标、官方渠道、状态标签和失败后的下一步动作；不把所有预订说明堆在首屏。

### 3.3 每日卡片：时间线是主内容

每个 D0—D9 区块包含：

- 日期圆标、星期、城市/区域和当天主标题。
- 交通、住宿、天气三个元信息。
- 时间线条目；普通条目可展开，重点景点和转场节点使用高亮卡。
- 当日“决策点”或“备用方案”提示。
- 住宿信息只在对应入住日出现，避免重复占用空间。

哈尔滨三天使用原稿内容：

- D1：抵达哈尔滨西站后入住中央大街附近，下午只做索菲亚外观、中央大街、防洪纪念塔和松花江边。
- D2：早上东北虎林园，午后哈工大校园开放区和航天馆；保留哈工大预约失败的替代逻辑。
- D3：上午哈药六厂南直路老厂区；下午根据 D552 是否正常开行决定保留或取消该安排，晚上抵达长白山站并接站。

### 3.4 天气卡：实时可用，失效可读

每一天按 `weatherCity + weatherDate` 请求天气接口，天气卡显示：

- 天气图标、天气文字、最低/最高温、风向/风力。
- 状态标签：`实时预报` 或 `计划参考`。
- 一句行动建议：如“山顶风大，带雨衣和薄外套”“高温/大雨时取消红梅文创园”。

天气接口返回 404、网络失败或日期超出可查询范围时，不显示虚构的精确天气；退回到按城市的夏季参考区间，并标注“出发前 1 天以官方预报为准”。

重点天气逻辑：

- D4 天池：天气决定是否上主峰；页面突出“开放以景区当天调度为准”。
- D5 备用日：天气不佳时显示二次入园、退票回流、温泉和小镇休整选项。
- D8 沈阳：高温或下雨时保留工业博物馆，红梅文创园自动标为可取消。

### 3.5 底部日期导航

保留移动端横向滚动日期导航，标签改为：出发、哈尔滨、虎园/哈工大、转场、天池、备用、沈阳、故宫、工业、返程。桌面端同时提供较宽的日期索引，当前日期跟随滚动高亮。

## 4. 数据与组件设计

### 4.1 数据模型

继续使用单页本地常量，但收敛为以下类型：

- `DayData`：日期、城市、标题、住宿、交通、天气查询信息、时间线、当天提示。
- `TimelineEntry`：时间、标题、正文、重点标记、标签、备用方案。
- `ReservationItem`：截止时间、目标、渠道、动作、状态类型。
- `WeatherState`：图标、天气文字、温度、风向/风力、来源状态、建议。

所有文案在页面数据区维护，组件只负责渲染；这样后续修正车次或预约时间时不需要改 JSX 结构。

### 4.2 组件边界

在现有页面内拆出轻量渲染组件或局部函数：

- `HeroSummary`：标题、统计、路线和提醒。
- `ReservationRail`：关键预约节点。
- `WeatherCard`：天气状态和行动建议。
- `DaySection`：日期头、天气、时间线和住宿。
- `TimelineItem`：普通折叠项和重点景点卡。
- `FallbackCard`：转场、天池、预约失败等调整逻辑。

不引入新的路由或状态管理库，使用现有 `activeDay`、`openItems`、滚动观察器和天气请求状态。

## 5. 天气数据流与容错

1. 页面挂载时收集所有带城市和日期的行程条目。
2. 调用现有 `api.batchWeather`，按城市/日期映射到对应 D 日。
3. 成功时显示动态天气；单个日期失败时只影响该天，不阻塞整页。
4. 请求失败时保留静态参考温度和天气建议，并显示“计划参考”。
5. 页面底部注明：天气和景区开放状态属于出发前及当天需复核的信息。

天气图标映射覆盖晴、多云、阴、雨、雪、风/雾/霾；未知文本统一使用阴天图标，避免出现空白状态。

## 6. 视觉与响应式规则

- 保留原页面偏纸张/旅行手帐的暖色基础，但降低大面积装饰，提升信息层级。
- 背景、正文和辅助文字对比度满足可读性；所有交互按钮保留至少 44px 触控区域。
- 移动端：单列、日期导航横向滚动、天气和住宿信息允许换行。
- 桌面端：最大内容宽度约 900px；总览和关键节点可以两列，日程仍保持单列时间线以减少跳读。
- 动效只用于页面进入、卡片展开和滚动导航，不影响内容阅读。
- 导航链接、按钮和折叠项提供 `aria-label`、`aria-expanded` 或可见焦点样式。
